# 10 — Feature: Violations Register

## Goal

When a representative returns a machine with the wrong battery, no charger, no carton, or physical
damage, the hand-off is **still accepted** — but it is recorded against him. Each representative has
a violation file the supervisor and Director can open at any time.

## Auto-detection rules

Run on confirm of any transfer whose rule has `runViolationChecks: true` (primarily the return legs
`REPRESENTATIVE_TO_BRANCH`, `MERCHANT_TO_REPRESENTATIVE`, `BRANCH_TO_COMPANY`).

| Condition | Violation type | Default severity | Charged to |
|---|---|---|---|
| `batterySerialScanned ≠ bonded battery serial` | `BATTERY_MISMATCH` | HIGH | the representative in `from_party` |
| `hasCharger = false` while the outbound record said true | `MISSING_CHARGER` | MEDIUM | same |
| `hasBox = false` while the machine was issued boxed | `MISSING_BOX` | LOW | same |
| `condition = DAMAGED / NOT_WORKING` while issued `GOOD` | `PHYSICAL_DAMAGE` | HIGH | same |
| machine held > `IDLE_ALERT_DAYS` without movement | `LATE_RETURN` | LOW | current holder |

**The comparison baseline** is the last confirmed *outbound* transfer item for that machine to that
person. Implement a helper `getLastOutboundItem(machineId, userId)` — do not compare against the
machine row, which reflects the present, not what he was handed.

## DTOs

```ts
export class CreateViolationDto {
  @IsUUID() violationTypeId: string;
  @IsUUID() userId: string;                       // who is held responsible
  @IsOptional() @IsUUID() machineId?: string;
  @IsOptional() @IsUUID() transferItemId?: string;
  @IsEnum(Severity) severity: 'LOW'|'MEDIUM'|'HIGH';
  @IsString() @MaxLength(1000) description: string;
}

export class ChargeViolationDto {
  @IsNumber() @Min(0.01) amount: number;
  @IsUUID() paymentMethodId: string;
  @IsDateString() chargedAt: string;
  @IsOptional() @IsString() notes?: string;
}

export class WaiveViolationDto {
  @IsString() @MinLength(5) @MaxLength(500) reason: string;
}
```

## Lifecycle

```
OPEN ──acknowledge──► ACKNOWLEDGED ──charge──► CHARGED ──► CLOSED
  │                        │
  └────────waive───────────┴──────────────────► WAIVED
```

- `OPEN` — created automatically or manually.
- `ACKNOWLEDGED` — the representative has seen it in the app (sets `acknowledged_at`).
- `CHARGED` — a monetary amount was assigned; an **income** `finance_transactions` row is created
  under the system category `VIOLATION_CHARGES`, `source = AUTO_VIOLATION`,
  `source_ref_type = 'violation'`. The transaction id is stored back on the violation.
- `WAIVED` — forgiven with a mandatory reason. Never deleted.
- `CLOSED` — terminal.

## Business rules

1. Violations are **never deleted**, only waived. This is a disciplinary record.
2. A violation is always attached to a person. If the responsible person is genuinely unclear, it is
   attached to the last confirmed custodian and the description says so.
3. Auto-generated violations set `auto_generated = true` and cannot be edited, only
   waived/charged — this protects the audit trail from quiet edits.
4. Charging a violation is the only way it produces money. Charging twice → `409 ALREADY_CHARGED`.
5. Waiving requires `violations.waive`, which by default only the Director and supervisors hold.
6. A representative can always read his own violations regardless of `violations.read.all`.

## Notifications

- On auto-creation → push to the representative and his branch supervisor.
- On charge → push to the representative with the amount.
- Weekly digest to each supervisor: open violations in his branch.

## Tests

- confirming a return with a mismatched battery creates exactly one `BATTERY_MISMATCH` violation
- the same confirmation run twice creates no duplicate (guard by `transfer_item_id` + type)
- charging creates exactly one income transaction linked back to the violation
- an auto-generated violation cannot be edited
